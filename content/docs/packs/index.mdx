title: Packs

A **pack** is a bundle of NevoFlux extensions — [skills](/en/docs/skills),
[canvas tools](/en/docs/canvas/tool-whitelist), starter [knowledge-base](/en/docs/knowledge-base)
pages, and a [Canvas](/en/docs/canvas) dashboard — installed from a single `pack.toml`
manifest. One install drops everything into place; one uninstall takes it cleanly back
out.

NevoFlux 0.3.16 accepts `pack-protocol/0.1` and `pack-protocol/0.2` manifests.
Version 0.2 adds components that change how the agent *behaves* rather than what is
installed, so they are worth understanding before you install one.

## What a pack can bundle

| Component | What it adds | Lands in |
|---|---|---|
| **Skills** | reusable agent capabilities | `~/.config/nevoflux/skills/` |
| **Canvas tools** | whitelisted command / internal tools | `~/.config/nevoflux/canvas-tools/` |
| **Seed pages** | starter knowledge-base pages you can edit | GBrain (only if absent) |
| **Dashboard** | a persistent Canvas micro-app | My Canvas |

Every component is optional — a pack can ship any subset.

### What a 0.2 pack can also do

| Component | What it does | When it applies |
|---|---|---|
| **Site rules** | refuse a tool, or ask you first, on matching sites — e.g. ask before any click on your bank | while the pack is active, or always if it says `installed` |
| **Hook** | a WebAssembly check that can refuse or question a tool call before it runs | while the pack is active, or always if `installed` |
| **Prompt replacement** | lets the agent replace its own system prompt on the pack's behalf | only while the pack is active |
| **Dashboard capabilities** | the browser actions and daemon commands the pack's dashboard may use; it gets nothing it did not declare | whenever the dashboard runs |

Site rules and hooks can only make the agent **stricter** — a pack has no way to
allow anything your [Agent execution tier](/en/docs/settings/general#agent-execution-tiers)
would not. Prompt replacement is the powerful one: a pack declaring `full` can
replace the agent's entire instructions while it is active. The permission checks
themselves live in code, not in the prompt, so they are unaffected.

### Active packs

Installing a pack makes its skills available everywhere. Its active-scope parts —
site rules, hooks and prompt replacement scoped to `active` — apply only once the
agent **activates** the pack (`pack_activate`), which it does when your goal
matches what the pack is for. Several packs can be active at once. Only 0.2 packs
can be activated.

Activation lives in the run that made it and the subagents it spawns; it never
carries over into another conversation. When the agent wants to deactivate a pack
whose rules are currently restricting it, it has to **ask you** — the agent cannot
lift a guard on itself — and in an unattended loop or schedule it simply cannot.

## What the platform guarantees

A pack author writes declarations and files; the daemon owns *how* to install and
uninstall. That gives you:

- **Transactional install** — if any step fails, everything already done is rolled back.
- **Idempotent** — re-installing the same version is a no-op; seed pages are written
  only if absent; the dashboard upserts by a fixed id.
- **Path-safe** — files only ever land in the whitelisted extension directories; a
  manifest can't escape them.
- **Clean, receipt-driven uninstall** — the platform records exactly what it placed and
  reverses precisely that. It **never deletes your knowledge-base data unless you
  explicitly ask to purge it**, and it skips files you've edited since install.

## Installing & managing packs

Three ways: the **Settings → Packs** panel, an **install link**, or the CLI.

### Settings → Packs

[Settings → Packs](/en/docs/settings/packs) lists your installed packs and installs new
ones from either a local `pack.toml` path or a **GitHub source**. Remote sources run an
**inspect → preview → confirm** flow before anything is written. Per-row **Update** and
**Uninstall** are available, with an optional "also delete this pack's data" choice that
is **off by default**.

The preview lists the pack's skills, canvas tools and the binaries they run, seed
pages, the dashboard, and the daemon commands the dashboard declares. It **does
not yet show** a 0.2 pack's site rules, hook, or prompt-replacement mode — read the
`[[components.tool_policy]]`, `[components.hooks]` and `[components.prompt]` sections
of its `pack.toml` before installing a pack you don't already trust.

### Install link (packhub)

Packs can be offered for install from a single link anywhere — a website, a README, or
the packhub catalog — via a deep link:

```
nevoflux://pack-install?src=<github-source>
```

`<github-source>` is **GitHub-only**: the shorthand `github:owner/repo[/sub][@ref]`, or a
`https://github.com/owner/repo[/tree/ref/sub]` URL. Clicking the link opens a dedicated
install page that runs the same **inspect → preview → confirm** flow as Settings → Packs —
it previews the contents, flags bundled tool binaries, blocks on policy violations, and
requires an explicit **Install** click before anything is written (already-installed packs
show **Update** / **Reinstall** instead). A link can only *offer* an install — it never
performs one silently.

```
nevoflux://pack-install?src=github:owner/repo
nevoflux://pack-install?src=github:owner/repo@v1.0.0
nevoflux://pack-install?src=https://github.com/owner/repo
```

Pin a `@ref` (tag or commit) for reproducible installs. To put an install button on a web
page:

```html
<a href="nevoflux://pack-install?src=github:owner/repo@v1.0.0">Install in NevoFlux</a>
```

### CLI

The CLI needs a running daemon:

```bash
nevoflux pack validate  <path/to/pack.toml>   # dry capability check, no writes
nevoflux pack install   <path/to/pack.toml> [--force]
nevoflux pack list                            # installed packs
nevoflux pack status    <name>                # version, component counts, deps
nevoflux pack update    <path/to/pack.toml>
nevoflux pack uninstall <name> [--purge-data] [--force]
```
